# AstrWeChat 1.3.0：主程序改名后 WCDB -1006 排查报告

分析日期：2026-09-19

## 结论与证据强度

高置信判断：当前分发的原生 WCDB 适配层带有与宿主程序身份相关的兼容性/保护限制。安装版把主程序保留为 WeFlow.exe 是现有工程刻意做的兼容处理，而不是漏改品牌。将其直接重命名会改变原生层可见的宿主身份，与用户报告的初始化 -1006 现象一致。

已确认：应用代码中的兼容配置、原生初始化失败传播位置、DLL 内部相关字符串，以及安装版与工程 DLL 完全一致。

尚未确认：DLL 中完整的文件名判定控制流、完整允许列表、是否同时校验其他身份字段。本轮没有成功进行完整反汇编，也没有执行改名前后的动态对照，因此不把字符串命中等同于已证明完整白名单。

## 范围与操作边界

用户授权排查 1.3.0 安装版改名导致的连接失败，要求暂不修改代码。
本轮读取项目源码、安装目录 DLL、现有 WCDB 日志；未改应用源代码、配置、DLL、EXE、数据库或安装目录，也未重启程序、重命名程序、重新打包或调用数据库初始化。本文件为新增的排查文档。
分析依赖下载尝试因本机 pip 代理异常失败；未据此声称完成反汇编。

## Evidence → Finding → Path

### E1：打包配置保留旧可执行文件名

位置：`1.3.0/package.json:70`、`:280`。

- 对外 productName 为 AstrWeChat。
- 顶层 executableName 为 WeFlow。
- installer.nsh:7 明确说明 WeFlow.exe 保持 WCDB 兼容，安装根目录使用 astrwechat。

F1：展示品牌和原生运行身份目前被有意分开。
P1：只修改展示名称或安装目录，并不等于已解除实际可执行文件名限制。

### E2：主进程刻意保留内部名称

位置：`1.3.0/electron/main.ts:30-37`。

注释明确说明原生初始化需要旧内部名称；代码执行 app.setName('WeFlow') 并保留 weflow 用户数据目录。

F2：现有工程已明确考虑 WCDB 的旧身份兼容问题。
P2：不能把 app.setName、productName 和磁盘上的 EXE 文件名当作同一个设置；用户已经在 app.setName 保留旧名称的情况下报告 EXE 改名失败。

### E3：错误来自原生初始化阶段

位置：`1.3.0/electron/services/wcdbCore.ts:925`、`:1403-1410`、`:397`。

代码绑定 int32 wcdb_init()，直接调用它；非零结果会记录原生日志并返回初始化失败。-1006 的应用层提示为原生安全校验未通过。

F3：这条失败路径位于 WCDB 引擎初始化，不是查询聊天记录时的 SQL 错误。
P3：排查重点应放在 wcdb_api.dll 的初始化/身份约束，而不是先重置数据库、删除缓存或反复更换数据库密钥。

### E4：原生 DLL 中存在宿主名称与保护相关内容

目标：`1.3.0/resources/wcdb/win32/x64/wcdb_api.dll`。

只读扫描发现以下文件偏移：

- 0x6CA9A、0x6CAAB：代码节中的 electron 与 .exe 立即数字节片段。
- 0x6CAD8：代码节中的 weflow.e 立即数字节片段。
- 0x114F10：weflow。
- 0x114F28：wechatdataanalysis.exe。
- 0x1160C8：InitProtection。
- 0x1160D8：wcdb_init [SecurityStatus:。
- 0x145E18：GetModuleFileNameA。

F4：原生组件包含与宿主名称和安全初始化相关的内容，支持身份检查方向；字符串扫描本身不能证明每个字符串的用途，也不能直接推导完整允许列表。
P4：后续应针对相关名称引用、宿主路径获取与 wcdb_init 失败分支做定向反汇编，或在隔离副本中做动态对照。

### E5：安装版与工程原生库完全一致

比较对象：

- `1.3.0/resources/wcdb/win32/x64/wcdb_api.dll`
- `C:/Program Files/astrwechat/resources/resources/wcdb/win32/x64/wcdb_api.dll`

两者 SHA-256 均为：

`6397760DA70DE8062829FBE6A2EC01CF0616D6F2B334E6FE54873898F38F7AD7`

F5：工程目录 DLL 的分析适用于当前本机安装版的同一文件，不存在这两个对象版本不一致的问题。

### E6：已有日志不能当作本次改名的直接复现

读取 `C:/Users/tiger/AppData/Roaming/weflow/logs/wcdb.log`。其中确有历史 -1006，但检索到的 runtime identity 只包含 WeFlow.exe 和开发环境 electron.exe，没有改名后的运行身份记录。部分旧错误来自同一进程先成功打开账号之后的再次初始化。

F6：-1006 不是文件改名专属错误，不能将历史的所有 -1006 都归因于改名。
P6：后续对照必须使用各自全新进程，并区分重复初始化与宿主改名两个变量。

## 对完全自主品牌命名的影响

1. 当前可以保留对外 AstrWeChat 展示、安装目录与快捷方式名称，内部继续使用 WeFlow.exe；这是兼容方案，不满足所有内部名称都自有的目标。
2. 若需要真实进程文件名也改成 AstrWeChat.exe，应优先取得支持自有宿主身份的原生适配层版本，或在具备源码和相应许可的情况下修改、重编译该层，再统一调整应用命名并回归测试。
3. 本轮限定检索的 resources 与 electron 目录中没有发现 InitProtection/wcdb_init 的 C/C++/Rust 实现；当前查到的是 TypeScript 绑定和预编译 DLL。
4. 只改 package.json 的 executableName，或者只改 app.setName，不能据现有证据认定足以解决。把 -1006 忽略并继续运行同样不是正确修复。
5. 安装目录、内部应用名、用户数据目录是否各自受到独立检查仍需验证，不能推断它们都必须改或都可以随意改。用户数据目录改动还需考虑原有配置迁移。

## 建议的下一步验证，尚未执行

在隔离的安装副本中，保持 DLL、资源、配置和数据库输入一致，仅改变宿主 EXE 文件名；原名和新名分别启动全新进程，记录实际 execPath、InitProtection 返回值、wcdb_init 返回值和最新原生日志。结合静态引用定位确认确切规则后，再设计支持自有命名的修复，不直接对现有安装程序或 DLL 做盲目替换。
